# Vehicle Traffic Analytics

An end-to-end Python baseline for monocular, fixed-camera traffic video. It detects COCO vehicles with Ultralytics YOLO, keeps IDs with ByteTrack, projects vehicle ground-contact points to a calibrated road plane, estimates smoothed speeds, counts crossings of a virtual line, and writes an annotated video plus CSV and JSON summaries.

## Install

Use Python 3.10 or newer in a virtual environment. Install a PyTorch build suitable for your CPU/CUDA setup if you need a specific accelerator build, then install this project's packages:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

On Windows, if PyTorch installation fails with a path-too-long error, create the virtual environment in a short path (for example `C:\\venvs\\vta`) or use a short project checkout path. PyTorch contains deeply nested package files.

Ultralytics downloads the selected weights (by default `yolo11n.pt`) on first use if they are not already present. The first inference run therefore needs access to the weights or a locally available model file. For GPU inference, use `--device 0`; use `--device cpu` to force CPU inference.

## 1. Calibrate the road plane

Measure a rectangular patch of road that is visible in the video. Run calibration on the same camera framing and video resolution that you will process:

```powershell
python calibrate.py "data\traffic.mp4" --width-m 7.0 --length-m 30.0
```

Replace the example dimensions with measured dimensions for your camera scene. In the first frame window, click four ground-plane points in this order:

1. Near-left corner of the measured road rectangle.
2. Near-right corner.
3. Far-right corner.
4. Far-left corner.

Press Enter to save `homography_config.json`. Press `R` to reset, right-click to undo the last point, or Esc to cancel. The calibrated metric axes are `x = near-left to near-right` and `y = near edge to far edge`. `--output` changes the JSON path.

The script maps the four image points to `(0, 0)`, `(width, 0)`, `(width, length)`, and `(0, length)` using OpenCV's four-point perspective transform. Inference uses the saved image-to-BEV matrix and `cv2.perspectiveTransform` for each vehicle's bottom-center anchor. [OpenCV documents the four-correspondence perspective transform](https://docs.opencv.org/4.10.0/da/d54/group__imgproc__transform.html).

## 2. Run inference and traffic analysis

```powershell
python main.py "data\traffic.mp4" --calibration homography_config.json --model yolo11n.pt
```

The default output files are `results/annotated.mp4`, `results/traffic_log.csv`, and `results/traffic_summary.json`. Show a live preview and stop it with Q by adding `--display`. Common options:

```text
--model yolo11n.pt                 model weights or a local model path
--tracker bytetrack.yaml           Ultralytics ByteTrack tracker config
--unit kmh                         kmh or mph for labels and CSV values
--smooth-window 8                  rolling speed-average length per track
--fps 29.97                        override bad/missing FPS metadata
--device 0                         use GPU 0; cpu is also supported
--output-video results/site_a.mp4
--csv results/site_a.csv
--summary-json results/site_a.json
```

The program reads the video's FPS metadata by default and uses frame-index differences divided by FPS for elapsed time. Supply `--fps` only when metadata is absent or known to be wrong. Input width and height must match the calibration exactly; calibrate again after cropping, resizing, changing the camera zoom, or moving the camera. Ultralytics' tracking mode uses `persist=True` for sequential frames and accepts `bytetrack.yaml` as its tracker configuration. [Ultralytics tracking documentation](https://docs.ultralytics.com/modes/track).

## Streamlit deployment

`streamlit_app.py` is a web interface for the same pipeline. It accepts a video upload, lets the user click the four calibration corners on the first frame, generates the homography, and provides the annotated video, CSV, and summary downloads. The public demo is CPU-only and limits clips to 120 seconds and 200 MB so a hosted run remains bounded. Uploaded clips and results are kept in temporary server storage for the session.

To deploy on Streamlit Community Cloud, use the public GitHub repository, branch `main`, and entrypoint `streamlit_app.py`. The root `requirements.txt` declares Python dependencies; `packages.txt` declares the Linux libraries needed by OpenCV. Streamlit Community Cloud deploys from a GitHub repository and uses the repository's dependency files when building the app ([deployment guide](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/deploy), [dependency guide](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/app-dependencies)). The model weights download on first launch, so the first startup can take longer than later runs.

## Calibration and counting behavior

- The speed anchor is the bottom-center of each detection box, approximating the tire/road contact location. Homography speeds are meaningful only for points on the calibrated road plane.
- The default count line crosses the middle of the calibrated rectangle. To move it, edit `count_line_bev_meters` in `homography_config.json` to `[[x1, y1], [x2, y2]]`, with coordinates in meters and both endpoints inside the calibrated rectangle.
- CSV rows are emitted once per track ID when that ID crosses the finite count-line segment. `timestamp` is elapsed media time (`HH:MM:SS.mmm`); `avg_speed` is the rolling mean at crossing in the selected unit and is blank if no valid speed sample exists. `direction` is `negative_to_positive` or `positive_to_negative` relative to the oriented line endpoints. For the generated horizontal line, those map to `toward_far` and `toward_near`, as recorded in the calibration JSON.
- `traffic_summary.json` contains crossing totals by class and direction, plus the mean of available per-vehicle crossing speeds. The HUD reports the crossing count and the mean current rolling speed of active tracks.
- `--max-speed-kmh` rejects physically implausible individual samples; `--max-speed-gap-frames` prevents a long occlusion gap from becoming a single large speed update. Tune these to the site and expected speeds.

## Validation and edge cases

- **Occlusion and ID switches:** ByteTrack has no appearance re-identification. Dense traffic and long occlusions can split or swap IDs, which affects trails and can cause a vehicle to be counted twice if its ID changes before/after the line. Review a representative annotated clip and tune detector confidence and tracker settings for the scene.
- **Far-field perspective:** A four-point homography becomes sensitive to pixel error near the horizon. Calibrate a well-sized road patch, avoid using distant detections for speed/counts, and consider a longer measured rectangle with surveyed points or multiple road zones when accuracy there matters.
- **Calibration quality:** Use four coplanar road points, not vehicle corners, shadows, or raised curbs. Confirm the rectangle ordering and real dimensions. Do not use footage from a moved or zoomed camera with the old matrix.
- **Speed verification:** Compare measured speed for several vehicles with a trusted reference (radar, GPS, or a surveyed distance and timestamp interval). Validate in both travel directions and at near and far parts of the calibrated area. The pixel-to-meter scale, video FPS, frame drops, box-anchor jitter, and camera motion all affect the result. A fixed-camera planar homography is an estimate, not a substitute for calibrated speed enforcement equipment.
- **Flow totals:** Counts are line-crossing events, not unique real-world registrations. Track ID fragmentation can affect totals. The CSV intentionally stores crossing events rather than one row per frame.
